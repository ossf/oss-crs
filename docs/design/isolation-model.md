# CRS Isolation & Resource Sandboxing

## Overview

A fundamental design requirement of OSS-CRS is **strict multi-tenant isolation**. When multiple Cyber Reasoning Systems (CRSs) run concurrently—or when an autonomous CRS executes potentially untrusted code generated by an LLM—the framework must guarantee that:

1. CRSs cannot interfere with each other's execution or access each other's working state directly.
2. Resource starvation is prevented through hardware and memory boundaries.
3. Network access is constrained so CRSs only communicate with designated infrastructure services.
4. Host stability is preserved even when targets crash, spin in infinite loops, or trigger out-of-memory (OOM) conditions.

## 2. Resource Sandboxing (cgroup v2)

OSS-CRS leverages Linux **cgroup v2** delegation to enforce fine-grained, kernel-level resource sandboxing via Docker's `--cgroup-parent` flag.

### Cgroup Hierarchy

At startup, OSS-CRS constructs an isolated cgroup tree under the invoking user's slice:

```text
/sys/fs/cgroup/user.slice/user-<uid>.slice/user@<uid>.service/oss-crs/
└── <run-id>-<phase>-<timestamp>-<rand>/
    ├── cgroup.subtree_control (+cpuset +memory)
    ├── <crs-name-1>/
    │   ├── cpuset.cpus (e.g., "0-3")
    │   ├── memory.max (e.g., 8589934592)
    │   ├── memory.swap.max ("0")
    │   └── cgroup.subtree_control (+cpuset +memory)
    └── <crs-name-2>/
        ...
```

### CPU Pinning (`cpuset.cpus`)
- Each CRS entry in `crs-compose.yaml` specifies a `cpuset` (e.g., `"0-3"`, `"4-7"`).
- Containers belonging to that CRS are restricted to the assigned physical CPU cores, preventing CPU contention between rival CRSs or background services.

### Memory Cap & OOM Handling (`memory.max` & `memory.swap.max`)
- Hard memory boundaries are specified in `crs-compose.yaml` (e.g., `memory: "16G"`).
- **Swap Suppression**: `memory.swap.max` is explicitly set to `"0"`. This enforces a hard memory ceiling and prevents the kernel from thrashing swap memory when an aggressive fuzzer leaks memory.
- If a container exceeds its memory limit, the Linux kernel OOM-killer immediately terminates the offending process with exit code `137` without starving sibling containers.

### Standard Fallback Mode
When cgroup-parent mode is not configured, OSS-CRS gracefully falls back to Docker Compose's standard container-level resource limits:
- `cpus` and `cpuset`
- `mem_limit` and `memswap_limit`

## 3. Network Isolation

CRSs communicate through isolated software-defined bridge networks created per campaign:

1. **Private CRS Networks (`<crs-name>-net`)**:
   - Each CRS has its own private Docker bridge network.
   - Modules within the same CRS can discover and communicate with each other using container service names.
   - Containers from other CRSs cannot join or access this network.

2. **Shared Infrastructure Network (`oss-crs-infra-net`)**:
   - Central infrastructure services (`litellm`, `postgres`, `exchange`, `webui`) attach to the shared infra network.
   - CRS modules attach to this network with external inter-container routing disabled, allowing egress only to designated infrastructure ports (LiteLLM proxy, WebUI publisher).
   - Direct inter-CRS container-to-container network traffic is strictly blocked.

## 4. Filesystem Isolation & Mount Boundaries

Containers within a CRS access the filesystem through tightly constrained mount points:

| Mount Point | Access Mode | Purpose |
|---|---|---|
| `OSS_CRS_TARGET_SOURCE` | **Read-Only** (`:ro`) | Host target source tree (prevents uncommitted source modification during fuzzing) |
| `OSS_CRS_FUZZ_PROJ` | **Read-Only** (`:ro`) | Target OSS-Fuzz configuration directory |
| `OSS_CRS_FETCH_DIR` | **Read-Only** (`:ro`) | Incoming shared data from other CRSs (managed by exchange sidecar) |
| `OSS_CRS_SUBMIT_DIR` | **Read-Write** (`:rw`) | Per-CRS outgoing artifacts directory |
| `OSS_CRS_SHARED_DIR` | **Read-Write** (`:rw`) | Scoped scratch directory shared only between modules of the same CRS |
| `OSS_CRS_LOG_DIR` | **Read-Write** (`:rw`) | Host-persisted CRS log directory |

No CRS container is ever given write access to the shared `EXCHANGE_DIR` or another CRS's submission directories. All cross-CRS artifact dissemination is arbitrated through the trusted `exchange` sidecar.
